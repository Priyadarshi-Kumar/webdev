A React **component** is a function. A **render** is React calling that function and turning the object it returns into DOM. A **re-render** is the same call again — same function, same slot in the tree — so <Term id="react-hook">hooks</Term> can line up with last time.

React does not watch your JSX or diff your source code. It keeps a tree of **fibers** (one per component instance). When something marks a fiber dirty, React runs that function again.

This note covers when that happens, what the two phases do, and a **MiniReact** you can hold in your head. MiniReact is a teaching sketch: no <Term id="concurrent-rendering">concurrent rendering</Term>, no list keys, no <Term id="hydration">hydration</Term>. The real scheduler does more; the data model is the same.

## A render is a function call

**Plain English:** A render is a function call — concepts first, then code.

```tsx
function Counter({ label }: { label: string }) {
  const [n, setN] = useState(0);
  return (
    <button type="button" onClick={() => setN((x) => x + 1)}>
      {label}: {n}
    </button>
  );
}
```

**First paint:** React calls `Counter({ label: "Score" })`. `useState(0)` creates a box whose current value is `0`. The return value describes a button — it is not the button itself. React then **commits** that description to the DOM.

**Click:** `setN` writes `1` into that same box and asks React to render `Counter` again. On the second call, `useState(0)` does **not** reset to `0`. It returns the box that already holds `1`. The `0` is only the initial value for a box that does not exist yet.

That is the whole trick: **the function is stateless; the fiber next to it is not.**

## When React schedules another render

**Plain English:** When this applies — and when to skip it.

### State or reducer on that fiber

`setState`, `useReducer`’s `dispatch`, and setters from `useSyncExternalStore` (when the store emitted) mark the fiber dirty. This is the usual click / fetch / input path.

Updates in the same event are **batched**. Two `setN` calls in one click still produce **one** re-render.

```tsx
function bump() {
  setN((n) => n + 1);
  setN((n) => n + 1); // still one render; n goes 0 → 2
}
```

### The parent rendered

If `App` re-renders, React calls `App` again, then (by default) calls **every child function** `App` returned — even when that child’s props look the same. Props are just arguments. A new parent render is a new child call unless you skip it (`memo`, or the <Term id="react-compiler">React Compiler</Term> proving the output cannot change).

```tsx
function App() {
  const [n, setN] = useState(0);
  return (
    <>
      <button type="button" onClick={() => setN((x) => x + 1)}>
        {n}
      </button>
      <Expensive /> {/* runs again every click unless memoized */}
    </>
  );
}
```

### Context the component (or a hook it uses) reads

`useContext(Theme)` subscribes that fiber to `Theme`. When the provider’s `value` is a new reference (React uses `Object.is`), every consumer re-renders.

A parent that does not read the context can still re-render if it has state of its own. Context does not skip parents.

### What does not, by itself, re-render a component

- Mutating a field on an object already in state (`user.name = "Ada"`) — React never sees a `setState`.
- Changing a ref (`ref.current = …`) — refs skip render on purpose.
- Props changing **without** a parent render — they cannot; props arrive because the parent ran.
- "The screen looks different" from CSS or DOM you edited by hand — React's tree is unchanged.

`memo(Child)` skips the child function when props are `Object.is`-equal to last time. It does not skip the child if the child has its own state update, or if it reads a context that changed.

In development, Strict Mode may call your function **twice** for the same update so impure renders show up. That is not two commits.

## Internally: render, then commit

**Plain English:** Internally: render, then commit — concepts first, then code.

React 18+ still has two big phases. Concurrent features can **pause** the first one, but the picture is the same.

### Render: call components, build a new tree

For each dirty fiber, React:

1. Sets "the current fiber" so hooks know which list to read.
2. Calls `Component(props)`.
3. Walks the returned element tree and **reconciles** it with the last tree: same `type` + same `key` → reuse the fiber and its hooks; different type → throw the old fiber away (state reset).
4. Repeats for children.

This phase should be **pure**: compute the next UI. Touching the real DOM here fights the commit and breaks <Term id="concurrent-rendering">concurrent</Term> renders that might be discarded.

### Commit: touch the DOM

When the tree is ready, React applies the diffs: insert nodes, update attributes, remove nodes, then run layout effects, then paint, then `useEffect`.

Effects are **not** the render. They run because a render committed.

That split is why React can throw away a render (user typed again) without leaving half-updated DOM.

## Hooks are a list on the fiber

**Plain English:** Hooks are a list on the fiber — concepts first, then code.

Each function component fiber has a linked list (or array) of hook cells: state, effect deps, memo, ref, …

```txt
fiber (Counter)
  hooks[0]  useState  → { state: 1, queue: … }
  hooks[1]  useEffect → { deps: [id], destroy: fn }
```

On every render React walks that list in **call order**. `useState` #1 is always cell 0. That is why hooks cannot sit in `if` — the next render would read the wrong cell and you get a <Term id="stale-closure">stale</Term> or corrupted tree.

`useState` is "read cell `i`, or create it with `initial`." `setState` is "write the cell, mark this fiber dirty, schedule work."

## MiniReact: enough to feel the internals

**Plain English:** MiniReact: enough to feel the internals — concepts first, then code.

The following runs in a browser. It supports function components, `useState`, host tags (`div`, `button`, `span`), strings as children, and **one** component root. No keys, no context, no fragments.

That is enough to see: **hooks live on the instance, render is a call, commit patches the DOM.**

### createElement (what JSX becomes)

```js
function createElement(type, props, ...children) {
  return {
    type,
    props: {
      ...(props ?? {}),
      children: children.flat().filter((c) => c != null && c !== false),
    },
  };
}
```

`function App() { return <Counter label="Score" />; }` compiles to `createElement(Counter, { label: "Score" })`. MiniReact never parses JSX itself.

### The hook slot and the scheduler

```js
let currentFiber = null;
let hookIndex = 0;
let nextUnit = null;
const scheduled = new Set();

function getHook(initial) {
  const fiber = currentFiber;
  const i = hookIndex++;
  if (!fiber.hooks[i]) {
    fiber.hooks[i] = {
      state: typeof initial === "function" ? initial() : initial,
    };
  }
  return fiber.hooks[i];
}

function useState(initial) {
  const fiber = currentFiber;
  const hook = getHook(initial);

  function setState(update) {
    const prev = hook.state;
    const next = typeof update === "function" ? update(prev) : update;
    if (Object.is(prev, next)) return; // same as React: bail out
    hook.state = next;
    scheduled.add(fiber);
    queueMicrotask(flush);
  }

  return [hook.state, setState];
}

function flush() {
  const fibers = [...scheduled];
  scheduled.clear();
  for (const fiber of fibers) renderFiber(fiber);
}
```

`queueMicrotask` is a toy batch: every `setState` in the same turn shares one `flush`. React's batching is the same idea, with a real event / lane scheduler.

### Reconcile and commit

```js
function createFiber(element, parentDom) {
  return {
    type: element.type,
    props: element.props,
    parentDom,
    hooks: [],
    child: null,
    node: null,
  };
}

function renderFiber(fiber) {
  if (typeof fiber.type === "function") {
    currentFiber = fiber;
    hookIndex = 0;
    const out = fiber.type(fiber.props);
    currentFiber = null;
    reconcileChild(fiber, out);
    return;
  }

  commitHost(fiber);
}

function reconcileChild(parent, element) {
  const same =
    parent.child &&
    parent.child.type === element.type;

  if (same) {
    parent.child.props = element.props;
    renderFiber(parent.child);
    return;
  }

  if (parent.child?.node) parent.node?.replaceChildren();
  parent.child = createFiber(element, parent.node);
  renderFiber(parent.child);
}

function commitHost(fiber) {
  const { type, props } = fiber;
  if (typeof type !== "string") return;

  if (!fiber.node) {
    fiber.node = type === "TEXT"
      ? document.createTextNode("")
      : document.createElement(type);
    fiber.parentDom.appendChild(fiber.node);
  }

  if (type === "TEXT") {
    fiber.node.nodeValue = props.nodeValue;
    return;
  }

  fiber.node.replaceChildren();
  for (const [k, v] of Object.entries(props)) {
    if (k === "children" || v == null) continue;
    if (k.startsWith("on") && typeof v === "function") {
      const event = k.slice(2).toLowerCase();
      fiber.node["on" + k.slice(2)] = v;
      continue;
    }
    if (k === "className") fiber.node.setAttribute("class", v);
    else if (k !== "type" || type !== "input") fiber.node.setAttribute(k, String(v));
  }

  const kids = Array.isArray(props.children) ? props.children : [props.children];
  for (const child of kids) {
    if (typeof child === "string" || typeof child === "number") {
      fiber.node.appendChild(document.createTextNode(String(child)));
      continue;
    }
    if (child && typeof child === "object") {
      const kid = createFiber(child, fiber.node);
      renderFiber(kid);
    }
  }
}

function render(element, container) {
  container.replaceChildren();
  const root = createFiber(element, container);
  root.node = container;
  nextUnit = root;
  renderFiber(root);
}
```

Host commit here is naive: it rebuilds children of host nodes each time. Real React **diffs** host children. The important line is `same type → keep fiber.hooks`. Change `Counter` to `Other` in that slot, and MiniReact (like React) allocates a **new** fiber: state starts over.

### Put it together

```js
function Counter({ label }) {
  const [n, setN] = useState(0);
  return createElement(
    "button",
    { type: "button", onClick: () => setN((x) => x + 1) },
    `${label}: ${n}`,
  );
}

function App() {
  return createElement(Counter, { label: "Score" });
}

render(createElement(App, null), document.getElementById("root"));
```

Click the button: `setState` writes the hook cell, `flush` calls `renderFiber` on **that** `Counter` fiber, `useState` returns `1`, `commitHost` updates the button text. `App` does not run. That matches React when only the child's state changed.

If `App` had its own `useState` and you updated **App**, MiniReact would call `App` again, see `child.type === Counter`, **reuse** the child fiber, and `Counter` would re-render too — parent render pulls the child. Same as React without `memo`.

## What real React adds on top of this

**Plain English:** What real React adds on top of this — concepts first, then code.

- **Fibers as a linked list** (`child`, `sibling`, `return`) so work can pause mid-tree.
- **Lanes / priority** so a keystroke can jump ahead of a slow list.
- **Host diffing + keys** so a list item is not destroyed when its index changes.
- **Double buffering** (`current` vs `workInProgress`) so the screen keeps the last committed tree until commit.
- **Effects** after commit, with dep arrays compared by `Object.is` on each item.

Read MiniReact until the hook index and "same type, keep the fiber" feel obvious. Then the real source is the same story with a scheduler.
