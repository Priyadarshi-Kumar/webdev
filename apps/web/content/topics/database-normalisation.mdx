**Database normalisation** means organising tables so each fact is stored **once**, in the **right** table. You are not “making more tables for fun.” You are fixing a messy spreadsheet before it causes bugs.

This note walks one example — a **campus bookstore** — from a bad export to a clean schema. Read the sections in order: each normal form builds on the previous one.

## What problem are we solving?

Imagine one Excel sheet for orders:

```txt
order_id | customer           | books
1        | Ada, ada@uni.edu   | 111 SQL Internals x2, 222 POSIX x1
2        | Ada, ada@uni.edu   | 111 SQL Internals x1
```

Three things go wrong when you keep everything in one place:

| Problem | What happens |
| --- | --- |
| **Update anomaly** | Change Ada’s email in one row, forget another → two emails for one person |
| **Insert anomaly** | You cannot add a new book until someone buys it |
| **Delete anomaly** | Delete the last sale of a book → you lose the book title too |

Normalisation is a **checklist** that makes those mistakes hard to repeat.

## Normal forms at a glance

| Step | Name | Plain English |
| --- | --- | --- |
| 1 | **1NF** | One value per cell. No lists like “book1, book2” in a single cell |
| 2 | **2NF** | Every column depends on the **whole** primary key (important when the key has multiple columns) |
| 3 | **3NF** | No column should depend on another **non-key** column |
| 4 | **BCNF** | Every rule “X determines Y” must have X as a key (stricter 3NF) |
| 5 | **4NF / 5NF** | Rare in day-to-day apps; mostly interview extras |

**Mnemonic for 1NF–3NF:** “The key, the **whole** key, and **nothing but** the key.”

## Vocabulary (only what you need)

### Functional dependency

Write `A → B` to mean: **if two rows have the same `A`, they must have the same `B`.**

```txt
isbn → title           -- one ISBN always has one title
customer_id → email    -- one customer id, one email
```

### Keys

- **Primary key** — uniquely identifies a row (`order_id`, or `{order_id, line}`).
- **Composite key** — primary key made of **two or more** columns.
- **Candidate key** — any column set that could be the primary key.

You need composite keys to understand **2NF**. Single-column keys automatically pass 2NF.

## Step 0 — The messy table

Someone flattened an order into one wide row per line item. Lists are gone, but facts are duplicated:

| order_id | line | customer_id | customer_name | email | isbn | title | publisher | pub_city | qty | price |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 1 | C1 | Ada | ada@uni.edu | 111 | SQL Internals | DataPress | Pune | 2 | 40 |
| 1 | 2 | C1 | Ada | ada@uni.edu | 222 | POSIX | O'Reilly | Sebastopol | 1 | 55 |
| 2 | 1 | C1 | Ada | ada@uni.edu | 111 | SQL Internals | DataPress | Pune | 1 | 40 |

Primary key: `{order_id, line}`.

Problems still here:

- Ada’s name and email repeat on every line.
- Book title and publisher repeat whenever the same ISBN appears.
- `pub_city` describes the **publisher**, not the book directly.

We fix these one normal form at a time.

## 1NF — First normal form

### Rule

1. **Atomic cells** — one value per column (no comma-separated lists).
2. **No repeating groups** — no `book1`, `book2`, `book3` columns.
3. **Unique column names**, distinct rows.

Our table above is already in **1NF** (one row per order line). 1NF did not remove redundancy — it only stopped storing lists inside one cell.

```sql
-- Still redundant, but valid 1NF
CREATE TABLE order_line_1nf (
  order_id      int NOT NULL,
  line          int NOT NULL,
  customer_id   text NOT NULL,
  customer_name text NOT NULL,
  email         text NOT NULL,
  isbn          text NOT NULL,
  title         text NOT NULL,
  publisher     text NOT NULL,
  pub_city      text NOT NULL,
  qty           int NOT NULL,
  price         numeric NOT NULL,
  PRIMARY KEY (order_id, line)
);
```

**Takeaway:** 1NF = “looks like a proper SQL table.” Redundancy can remain.

## 2NF — Second normal form

### Rule

Table is in 1NF **and** every non-key column depends on the **entire** primary key — not just part of it.

Our key is `{order_id, line}`. Some columns only depend on **part** of that key:

| Column | Actually depends on | Problem |
| --- | --- | --- |
| `customer_name`, `email` | `customer_id` (via order) | Not on `{order_id, line}` directly |
| `title`, `publisher`, `pub_city` | `isbn` | Not on `{order_id, line}` |
| `qty`, `price` | `{order_id, line}` | OK — belongs on the line |

That “depends on part of the key” issue is a **partial dependency**. 2NF removes it by splitting tables.

### Dependencies we trust

```txt
{order_id, line} → isbn, qty, price
order_id         → customer_id
customer_id      → customer_name, email
isbn             → title, publisher, pub_city
```

### After 2NF — four tables

**customer** (key: `customer_id`):

| customer_id | customer_name | email |
| --- | --- | --- |
| C1 | Ada | ada@uni.edu |

**book** (key: `isbn`):

| isbn | title | publisher | pub_city |
| --- | --- | --- | --- |
| 111 | SQL Internals | DataPress | Pune |
| 222 | POSIX | O'Reilly | Sebastopol |

**orders** (key: `order_id`):

| order_id | customer_id |
| --- | --- |
| 1 | C1 |
| 2 | C1 |

**order_line** (key: `{order_id, line}`):

| order_id | line | isbn | qty | price |
| --- | --- | --- | --- | --- |
| 1 | 1 | 111 | 2 | 40 |
| 1 | 2 | 222 | 1 | 55 |
| 2 | 1 | 111 | 1 | 40 |

```sql
CREATE TABLE customer (
  customer_id   text PRIMARY KEY,
  customer_name text NOT NULL,
  email         text NOT NULL UNIQUE
);

CREATE TABLE book (
  isbn      text PRIMARY KEY,
  title     text NOT NULL,
  publisher text NOT NULL,
  pub_city  text NOT NULL
);

CREATE TABLE orders (
  order_id    int PRIMARY KEY,
  customer_id text NOT NULL REFERENCES customer (customer_id)
);

CREATE TABLE order_line (
  order_id int NOT NULL REFERENCES orders (order_id),
  line     int NOT NULL,
  isbn     text NOT NULL REFERENCES book (isbn),
  qty      int NOT NULL,
  price    numeric NOT NULL,
  PRIMARY KEY (order_id, line)
);
```

**Note on `price`:** it lives on `order_line` because it is what Ada **paid that day**. If catalogue prices change later, history stays correct.

**Takeaway:** 2NF matters when your primary key has **multiple columns**. Split facts that belong to `isbn`, `customer_id`, etc. into their own tables.

## 3NF — Third normal form

### Rule

Table is in 2NF **and** no non-key column depends on **another** non-key column.

On `book`, we still have:

```txt
isbn → publisher → pub_city
```

`pub_city` is really about the **publisher**, not the ISBN. That chain `key → A → B` where both `A` and `B` are non-keys is a **transitive dependency**.

### Fix — add a publisher table

**publisher** (key: `publisher_id`):

| publisher_id | name | city |
| --- | --- | --- |
| P1 | DataPress | Pune |
| P2 | O'Reilly | Sebastopol |

**book** (after 3NF):

| isbn | title | publisher_id |
| --- | --- | --- |
| 111 | SQL Internals | P1 |
| 222 | POSIX | P2 |

```sql
CREATE TABLE publisher (
  publisher_id text PRIMARY KEY,
  name         text NOT NULL,
  city         text NOT NULL
);

CREATE TABLE book (
  isbn         text PRIMARY KEY,
  title        text NOT NULL,
  publisher_id text NOT NULL REFERENCES publisher (publisher_id)
);
```

Move DataPress from Pune to Bengaluru **once** — every book follows.

### 2NF vs 3NF (quick compare)

| | Partial (2NF) | Transitive (3NF) |
| --- | --- | --- |
| **Pattern** | Composite key, column follows one part of key | Column follows another non-key column |
| **Example** | `title` depends on `isbn`, not `{order_id, line}` | `pub_city` depends on `publisher`, not `isbn` |
| **Fix** | Split `book`, `customer` out of line items | Split `publisher` out of `book` |

**Takeaway:** For most CRUD apps, **3NF is the design you want**: `customer`, `publisher`, `book`, `orders`, `order_line`.

## BCNF — Boyce–Codd normal form

### Rule (simpler wording)

For every rule `X → Y` in the table, **`X` must be a key** (or the rule is trivial).

3NF allows one edge case BCNF does not. You rarely design toward it — but interviews love it.

### Classic example — student, subject, teacher

Business rules:

- Each `(student, subject)` pair has **one** teacher.
- Each **teacher** teaches **one** subject only.

```txt
{student, subject} → teacher
teacher            → subject
```

| student | subject | teacher |
| --- | --- | --- |
| Ada | Databases | Dr Rao |
| Ada | Networks | Dr Sen |
| Gus | Databases | Dr Rao |

Pick `{student, subject}` as primary key. Column `teacher` is not a key, but `teacher → subject`. Table can still be **3NF** (textbook edge case). It is **not BCNF**.

**Anomalies:**

- Rename “Databases” → update every student row with Dr Rao.
- Cannot record “Dr Rao teaches Databases” until a student enrols.

### BCNF split

**teaches** (key: `teacher`):

| teacher | subject |
| --- | --- |
| Dr Rao | Databases |
| Dr Sen | Networks |

**enrolment** (key: `{student, teacher}`):

| student | teacher |
| --- | --- |
| Ada | Dr Rao |
| Ada | Dr Sen |
| Gus | Dr Rao |

```sql
CREATE TABLE teaches (
  teacher text PRIMARY KEY,
  subject text NOT NULL
);

CREATE TABLE enrolment (
  student text NOT NULL,
  teacher text NOT NULL REFERENCES teaches (teacher),
  PRIMARY KEY (student, teacher)
);
```

Join on `teacher` to recover the original rows. That join is **lossless** — you do not invent or lose data.

**Takeaway:** New OLTP schemas → aim for **BCNF**. The student/teacher example is the “gotcha” to recognise in interviews.

## 4NF and 5NF (interview extras)

Most product backends stop at 3NF/BCNF. Skim these if an interviewer asks “what comes after BCNF?”

### 4NF — independent lists

Problem: one row stores **two independent lists** that multiply against each other.

| employee | skill | language |
| --- | --- | --- |
| Ada | SQL | en |
| Ada | SQL | hi |
| Ada | Git | en |
| Ada | Git | hi |

Ada’s skills and languages are **independent** — storing both in one table forces a Cartesian product (2 skills × 2 languages = 4 rows).

**Fix:** separate `employee_skill` and `employee_language` tables.

### 5NF — join dependencies

Even rarer. A row `(agent, product, company)` might always be reconstructible from three pairwise tables **only when** a specific three-way business rule exists. Without that rule, splitting loses information.

**Interview one-liner:** “5NF is about join dependencies — if you cannot state the three-way rule, you are not in a 5NF problem.”

## How to normalise in an interview

Follow this sequence:

1. **List columns** and pick candidate keys.
2. **List dependencies** — ask the business; do not guess `city → zip` if multiple zips share a city.
3. **1NF** — split lists; one value per cell.
4. **2NF** — remove columns that depend on part of a composite key.
5. **3NF** — remove columns that depend on other non-key columns.
6. **BCNF** — check every `X → Y` has `X` as a key.
7. **Stop** unless they ask for 4NF/5NF.

## When denormalisation is OK

Normalisation is the default for **OLTP** (orders, users, payments). Sometimes you **copy** data on purpose:

| Good reason | Example |
| --- | --- |
| Read-heavy dashboard | `orders_today` with customer name baked in |
| Historical snapshot | `order_line.price` at purchase time |
| Data warehouse | Star schema with fact + dimension tables |

| Bad reason | Why |
| --- | --- |
| “Joins are slow” with no profiling | Add indexes and `EXPLAIN` first |
| Copy email onto every line “for the UI” | No sync story → stale data |

If you denormalise, document the **source of truth** and how updates propagate (trigger, job, app write).

## Cheat sheet

| Form | What it adds | What smell it fixes |
| --- | --- | --- |
| **1NF** | Atomic cells, no repeating groups | Lists in one cell, `item1`/`item2` columns |
| **2NF** | Full dependence on whole key | Title on line item when key is `{order_id, line}` |
| **3NF** | No non-key → non-key chains | City stored on book when it belongs to publisher |
| **BCNF** | Every determinant is a key | Teacher → subject edge case |
| **4NF** | Split independent multi-valued facts | Skill × language row explosion |
| **5NF** | Split join-dependent triples | Rare; needs explicit three-way rule |

The bookstore ends at **`customer`, `publisher`, `book`, `orders`, `order_line`** — a solid schema behind a [FastAPI](/blog/fastapi) or Node orders API.
