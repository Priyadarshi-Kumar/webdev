**Normalisation** (US: *normalization*) is a set of tests you run on a relational table so each fact is stored **once**, in **one place**, for a **reason**. You do not “make tables smaller for fun.” You remove **update, insert, and delete anomalies** that come from mixing independent facts in the same row.

The stages are ordered. **2NF assumes 1NF. 3NF assumes 2NF. BCNF is a stricter 3NF.** 4NF and 5NF show up less in day-to-day CRUD apps, but interviews still ask for the difference.

This note uses one running domain — a **campus bookstore** — then a second tiny schema where 3NF is not enough.

## Vocabulary you need first

### Functional dependency

Write `A → B` to mean: if two rows agree on `A`, they **must** agree on `B`. `A` **determines** `B`.

```txt
isbn → title          -- one ISBN, one title
isbn → publisher_id
publisher_id → publisher_name
```

`A` and `B` can be sets of columns: `{student_id, isbn} → purchased_at`.

A **superkey** is any set of columns that determines **every** column in the table. A **candidate key** is a superkey with no spare column. You pick one candidate key as the **primary key**; the others stay **alternate keys**.

A column is **prime** if it belongs to *any* candidate key, not only the primary key.

### The three anomalies

Suppose every sale row also copies the book title and the publisher’s phone:

| sale_id | isbn | title | publisher_phone | qty |
| --- | --- | --- | --- | --- |
| 1 | 111 | SQL Internals | 555-0100 | 2 |
| 2 | 111 | SQL Internals | 555-0100 | 1 |

- **Update:** change the publisher phone in one sale, forget the other → two phones for one publisher.
- **Insert:** you cannot record a new book until someone buys it (if `sale_id` is required).
- **Delete:** the last sale of a book disappears and you lose the title too.

Normal forms are a checklist that make those accidents structurally hard.

### What “normal form” is *not*

It is not “more tables = better.” A warehouse fact table that repeats `product_name` on purpose is **denormalised** for scan speed. You still *know* the dependency; you chose to violate 3NF. Normalisation is the default for **OLTP**. Analytics often undo it.

## Unnormalised starting point

### A spreadsheet that “works” until it does not

Someone exports orders into one sheet. Repeating groups sit in the same cell:

```txt
order_id | customer           | books
1        | Ada, ada@uni.edu   | 111 SQL Internals x2, 222 POSIX x1
2        | Ada, ada@uni.edu   | 111 SQL Internals x1
```

Problems stacked on problems: two facts in `customer`, a list in `books`, Ada’s email copied, titles copied next to ISBNs.

SQL has no honest type for “list of books in a cell.” You either split rows or you store JSON and give up relational integrity. First normal form is the split.

## 1NF — First normal form

### The rule

A relation is in **1NF** if:

1. Every intersection of row and column holds a **single** value (atomic for this model).
2. There are **no repeating groups** (`book1`, `book2`, `book3` columns, or a comma list meant as several tuples).
3. Rows are distinct; columns have unique names.

“Atomic” is relative. `2026-08-22` is one date, not three columns, unless you query year/month/day independently as keys. A JSON array of ISBNs is **not** 1NF if you still mean “several order lines.”

### The bookstore in 1NF

One row per **order line**. Customer fields still repeat. That is allowed in 1NF.

| order_id | line | customer_id | customer_name | email | isbn | title | publisher | pub_city | qty | price |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 1 | C1 | Ada | ada@uni.edu | 111 | SQL Internals | DataPress | Pune | 2 | 40 |
| 1 | 2 | C1 | Ada | ada@uni.edu | 222 | POSIX | O'Reilly | Sebastopol | 1 | 55 |
| 2 | 1 | C1 | Ada | ada@uni.edu | 111 | SQL Internals | DataPress | Pune | 1 | 40 |

Primary key: `{order_id, line}` (composite).

```sql
CREATE TABLE order_line_1nf (
  order_id      int NOT NULL,
  line          int NOT NULL,
  customer_id   text NOT NULL,
  customer_name text NOT NULL,
  email         text NOT NULL,
  isbn          text NOT NULL,
  title         text NOT NULL,
  publisher     text NOT NULL,
  pub_city      text NOT NULL,
  qty           int NOT NULL,
  price         numeric NOT NULL,
  PRIMARY KEY (order_id, line)
);
```

Ada’s email lives in **every** line. `title` is determined by `isbn`, not by `{order_id, line}`. 1NF only killed the list. It did not kill redundancy.

## 2NF — Second normal form

### The rule

A table is in **2NF** if it is in 1NF and **every non-prime column depends on the whole candidate key**, not a piece of it.

Partial dependency is the 2NF sin: key is `(order_id, line)`, but `customer_name` depends only on something else, and `title` depends only on `isbn`.

If the primary key is a **single** column, 2NF is automatic (there is no “part” of the key). Composite keys are where people fail 2NF.

### Split the bookstore

Dependencies we actually have:

```txt
{order_id, line} → isbn, qty, price
order_id         → customer_id
customer_id      → customer_name, email
isbn             → title, publisher, pub_city
```

2NF says: facts about `isbn` do not belong in a table keyed by `{order_id, line}`. Facts about the customer do not either — though some of those are **transitive** (3NF), not partial. In practice you split both while you are here.

**book** — key `isbn`:

| isbn | title | publisher | pub_city |
| --- | --- | --- | --- |
| 111 | SQL Internals | DataPress | Pune |
| 222 | POSIX | O'Reilly | Sebastopol |

**customer** — key `customer_id`:

| customer_id | customer_name | email |
| --- | --- | --- |
| C1 | Ada | ada@uni.edu |

**orders** — key `order_id`:

| order_id | customer_id |
| --- | --- |
| 1 | C1 |
| 2 | C1 |

**order_line** — key `{order_id, line}`:

| order_id | line | isbn | qty | price |
| --- | --- | --- | --- | --- |
| 1 | 1 | 111 | 2 | 40 |
| 1 | 2 | 222 | 1 | 55 |
| 2 | 1 | 111 | 1 | 40 |

```sql
CREATE TABLE customer (
  customer_id   text PRIMARY KEY,
  customer_name text NOT NULL,
  email         text NOT NULL UNIQUE
);

CREATE TABLE book (
  isbn      text PRIMARY KEY,
  title     text NOT NULL,
  publisher text NOT NULL,
  pub_city  text NOT NULL
);

CREATE TABLE orders (
  order_id    int PRIMARY KEY,
  customer_id text NOT NULL REFERENCES customer (customer_id)
);

CREATE TABLE order_line (
  order_id int NOT NULL REFERENCES orders (order_id),
  line     int NOT NULL,
  isbn     text NOT NULL REFERENCES book (isbn),
  qty      int NOT NULL,
  price    numeric NOT NULL,
  PRIMARY KEY (order_id, line)
);
```

`price` on the line is a **snapshot** of what Ada paid that day. It is *not* `isbn → price` if prices change. That is a real modelling choice: current catalogue price lives on `book`; historical charge lives on `order_line`.

`book` is still not 3NF: `pub_city` is really a fact about `publisher`.

## 3NF — Third normal form

### The rule

In 3NF, the table is in 2NF and **no non-prime column depends on another non-prime column**. In Codd’s wording: every non-prime attribute depends **only** on candidate keys — not transitively through some other description column.

The pattern is `K → A → B` where `K` is a key, `A` and `B` are non-keys, and you stored both `A` and `B` next to `K`. Then `B` is redundant: it follows from `A`.

Classic: `isbn → publisher → pub_city`. `pub_city` does not describe the book; it describes the publisher.

### Publisher pulled out

**publisher**:

| publisher_id | name | city |
| --- | --- | --- |
| P1 | DataPress | Pune |
| P2 | O'Reilly | Sebastopol |

**book** after 3NF:

| isbn | title | publisher_id |
| --- | --- | --- |
| 111 | SQL Internals | P1 |
| 222 | POSIX | P2 |

```sql
CREATE TABLE publisher (
  publisher_id text PRIMARY KEY,
  name         text NOT NULL,
  city         text NOT NULL
);

CREATE TABLE book (
  isbn          text PRIMARY KEY,
  title         text NOT NULL,
  publisher_id  text NOT NULL REFERENCES publisher (publisher_id)
);
```

Change Pune → Bengaluru **once**. Every DataPress book follows.

A common 3NF mnemonic: **“the key, the whole key, and nothing but the key.”** 1NF is “a table.” 2NF is “the whole key.” 3NF is “nothing but the key.” It is incomplete (BCNF exists) but it is the right instinct for CRUD schemas.

### Transitive vs partial

| Kind | Example | Fixed by |
| --- | --- | --- |
| Partial | `{order_id, line}` key, `title` from `isbn` only | 2NF |
| Transitive | `isbn → publisher_id → city` | 3NF |

If you only remember one interview sentence: **2NF is composite keys; 3NF is facts that depend on other facts, not on the key.**

## BCNF — Boyce–Codd normal form

### The rule

**Every determinant is a candidate key.** For every non-trivial `X → Y` in the table, `X` must be a superkey.

3NF still allows `X → Y` when `Y` is **prime** (part of some candidate key) and `X` is not a superkey. That leftover is rare and confusing. BCNF forbids it.

### Where 3NF is not enough

Drop the bookstore. A department assigns **one teacher per (student, subject)**, and **each teacher teaches only one subject**.

```txt
{student, subject} → teacher
teacher            → subject
```

Candidate keys: `{student, subject}` **and** `{student, teacher}` (if you know the student and the teacher, the subject follows).

| student | subject | teacher |
| --- | --- | --- |
| Ada | Databases | Dr Rao |
| Ada | Networks | Dr Sen |
| Gus | Databases | Dr Rao |

This table is in **3NF**: the only non-prime column is `teacher` if you pick `{student, subject}` as primary key… except `teacher` is also prime, because `{student, teacher}` is a candidate key. `teacher → subject` has a **prime** dependent, so 3NF is satisfied. BCNF is not: `teacher` determines `subject` but `teacher` is not a superkey (Dr Rao can teach many students).

Anomalies: rename “Databases” for Dr Rao and you must touch every student row. You cannot record “Dr Rao teaches Databases” until a student enrols.

BCNF decomposition:

**teaches** — key `teacher`:

| teacher | subject |
| --- | --- |
| Dr Rao | Databases |
| Dr Sen | Networks |

**enrolment** — key `{student, teacher}` (or `{student, subject}` once subject is implied):

| student | teacher |
| --- | --- |
| Ada | Dr Rao |
| Ada | Dr Sen |
| Gus | Dr Rao |

```sql
CREATE TABLE teaches (
  teacher text PRIMARY KEY,
  subject text NOT NULL
);

CREATE TABLE enrolment (
  student text NOT NULL,
  teacher text NOT NULL REFERENCES teaches (teacher),
  PRIMARY KEY (student, teacher)
);
```

Join them back on `teacher` and you recover the original relation. That is the point of a **lossless** decomposition.

### 3NF vs BCNF in one line

Keep 3NF if you must preserve **all** functional dependencies in one table and BCNF would split a dependency across tables. In new OLTP designs, **aim for BCNF**. The leftover 3NF-not-BCNF schemas are textbook traps, not a goal.

## 4NF — Fourth normal form

### The rule

The table is in BCNF, and it has **no independent multivalued dependencies**.

A **multivalued dependency** `A →→ B` means: for a given `A`, the set of `B` values is independent of the other columns. If Ada has skills SQL and Git, and languages `en` and `hi`, storing them in one table forces a **Cartesian product**.

| employee | skill | language |
| --- | --- | --- |
| Ada | SQL | en |
| Ada | SQL | hi |
| Ada | Git | en |
| Ada | Git | hi |

That is BCNF (the whole row is the key; there are no non-trivial FDs). It is not 4NF. Add skill `Linux` and you must insert **two** rows (one per language) or the independence is lost.

`employee →→ skill` and `employee →→ language` are two independent facts.

### Two tables

| employee | skill |
| --- | --- |
| Ada | SQL |
| Ada | Git |

| employee | language |
| --- | --- |
| Ada | en |
| Ada | hi |

```sql
CREATE TABLE employee_skill (
  employee text NOT NULL,
  skill    text NOT NULL,
  PRIMARY KEY (employee, skill)
);

CREATE TABLE employee_language (
  employee text NOT NULL,
  language text NOT NULL,
  PRIMARY KEY (employee, language)
);
```

If skill and language were **not** independent — “SQL is certified only in English” — that is a different dependency and you would **keep** a three-column table. 4NF is about independence, not about “never have three columns.”

## 5NF — Fifth normal form

### The rule

Also called **project-join normal form (PJNF)**. After 4NF, the only remaining issue is a **join dependency**: reconstructing the table always needs a join of **three or more** projections, not two.

Example: agents sell products for companies, and the constraint is:

> If agent *A* sells product *P*, and *P* is made by company *C*, and *A* represents *C*, then *A* sells *P* for *C*.

Storing the triple `(agent, product, company)` then repeats combinations that are already implied by the three pairwise tables. 5NF says: keep the pairwise relations if that constraint is real.

| agent | product | company |
| --- | --- | --- |
| Ada | DBMS | DataPress |
| Ada | POSIX | O'Reilly |
| Gus | DBMS | DataPress |

If the business also insists “Ada represents DataPress,” “Ada sells DBMS,” “DataPress makes DBMS,” the triple is a join of those three. Decompose only when that **cyclic** constraint is actually enforced. Most product schemas never reach this; inventing three tables without the constraint **loses** information (a **lossy** split).

Interview-level takeaway: **5NF is about join dependencies. If you cannot name the three-way rule, you are not in a 5NF problem.**

## Forms you will hear but rarely design toward

### DKNF

**Domain/key normal form:** every constraint is a logical consequence of domain constraints and key constraints. It is a cleanliness goal, not a mechanical “split this column” recipe. Check constraints and keys should imply the business rules you care about.

### 6NF

Used in some **temporal / anchor** models: a table is in 6NF if it is in 5NF and cannot be decomposed further except into keys plus **one** attribute (often with a time interval). Think “one fact per row” for bi-temporal warehouses, not for an orders API.

### Elementary key normal form (EKNF)

Sits between 3NF and BCNF. Almost nobody asks for it outside a theory paper. If you can explain BCNF, skip EKNF unless the interviewer names it.

## Walking an interview

### Order of attack

1. List attributes and **keys**.
2. List **functional dependencies** (ask the business; do not guess `city → zip` if one city has many zips).
3. 1NF: no lists, no `phone1`/`phone2`.
4. 2NF: no column that depends on **part** of a composite key.
5. 3NF: no `key → a → b` for non-keys `a`, `b`.
6. BCNF: every left-hand side of an FD is a key.
7. 4NF: independent multi-valued facts get their own tables.
8. Stop unless they explicitly want 5NF.

### Lossless join and dependency preservation

A split is **lossless** if joining the pieces can only produce rows that were legal in the original. BCNF decompositions can be made lossless; they do not always **preserve** every FD in a single table (you may need the join to check `teacher → subject`). That tradeoff is why textbooks keep 3NF around.

### Denormalise on purpose

Fine reasons:

- A **read model** / cache table for a dashboard (`orders_today` with customer name baked in).
- A data warehouse **star**: `dim_customer` still normalised-ish; `fact_sale` repeats `date_key` and degenerate IDs.
- An event **snapshot** (`order_line.price` as of purchase).

Bad reasons:

- “Joins are slow” with no index, no `EXPLAIN`, no row counts.
- Copying `customer.email` onto every line “so the UI is easier” without a sync story.

If you denormalise, name the **source of truth** and how updates flow (trigger, job, application write).

## Cheat sheet

| Form | Extra requirement beyond the previous | Smell it fixes |
| --- | --- | --- |
| 1NF | Atomic cells, no repeating groups | Lists in a cell, `item1`/`item2` columns |
| 2NF | Full dependence on the **whole** key | Composite key, some columns follow one part |
| 3NF | No transitive dependence of non-keys | `zip` stored next to `city` next to `id` |
| BCNF | Every FD’s left side is a key | 3NF table with overlapping candidate keys |
| 4NF | No independent `→→` in one table | Skill × language explosion |
| 5NF | No non-trivial join dependency | Triple that is always the join of three pairs |

The bookstore ends in 3NF/BCNF for ordinary FDs: `customer`, `publisher`, `book`, `orders`, `order_line`. That is the design you want behind a FastAPI or Node orders service. 4NF and 5NF are the follow-up when someone asks “and after BCNF?” — answer with independence of facts, then stop.
