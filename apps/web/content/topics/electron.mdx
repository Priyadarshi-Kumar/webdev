**Electron** ships a Chromium browser and a Node.js runtime in one installer. You write HTML, CSS, and JavaScript (or React) like a website, then you get a real macOS / Windows / Linux window: dock icon, menus, file dialogs, and `fs` access.

VS Code, Slack, Figma (desktop), Discord, and Notion’s desktop app are Electron. The UI is a web page. The “native” part is extra processes and APIs that a tab on the internet is not allowed to have.

This note is the **core model**, not a tour of every npm starter. If you understand **main**, **renderer**, **preload**, and **IPC**, every Electron + React template is the same machine with different folders.

## Why Electron exists

A website cannot:

- Read `/Users/you/Documents/notes.json` without the user picking a file
- Add a tray icon or a native menu bar
- Run when the browser is closed
- Ship as `MyApp.dmg` / `.exe` with one double-click

Electron’s bet: **reuse the web stack** (and React) and **wrap it in Chromium + Node**, instead of rewriting the UI in Swift / C# / Qt.

Cost of that bet: you ship a browser engine. Installers are tens to hundreds of MB. RAM is closer to “a Chrome tab plus Node” than to a tiny native widget. For many product teams that is acceptable because one codebase covers three operating systems.

## The process model (this is the core)

Electron is **not one JavaScript heap**. It is several OS processes that talk with messages.

```
┌─────────────────────────────────────────────────────────┐
│  Main process  (Node.js)                                │
│  app, BrowserWindow, dialog, Menu, Tray, ipcMain, fs    │
│  One per application                                    │
└───────────────────────────┬─────────────────────────────┘
                            │  IPC (structured clone)
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
┌───────────────────┐                 ┌───────────────────┐
│ Renderer (Chromium)│                 │ Renderer (Chromium)│
│ Window A — React   │                 │ Window B — React   │
│ DOM, fetch, CSS    │                 │ No Node by default │
└─────────┬─────────┘                 └───────────────────┘
          │
          │  contextBridge (preload)
          ▼
   window.notes.save(text)   ←  the only Node-shaped API React sees
```

### Main process

Starts when the user launches the app. It is **Node**. It does **not** have a DOM. Its jobs:

- Create and destroy windows (`BrowserWindow`)
- Native OS: `dialog`, `Menu`, `Tray`, `shell`, power monitor
- Own privileged work: filesystem, spawning child processes, talking to hardware
- Listen with `ipcMain` and answer renderers

There is **one** main process.

### Renderer process

Each window (and each `<webview>` / extra `BrowserView`) is a Chromium renderer. It has a **DOM**. React runs **here**.

By default in modern Electron, the renderer is a **normal web page**: no `require`, no `fs`, no `process.versions` except what you expose. That is on purpose. If a XSS bug in React could call `fs.rmSync("/")`, a desktop app would be a malware kit.

### GPU / utility processes

Chromium still uses extra processes (GPU, network, etc.). You rarely write code for them. You still feel them in Activity Monitor as several “MyApp Helper” entries.

### What React is allowed to do

React in the renderer is the same React you already know: components, hooks, state. It **cannot** import `fs` from `node:fs` unless you turn on dangerous flags. The supported path is:

1. React calls a **tiny API** on `window` (you define it)
2. **Preload** forwards that call over IPC
3. **Main** does the Node work and returns a result

That three-step hop **is** Electron’s security model.

## BrowserWindow — how a laptop window appears

```js
// electron/main.js  (main process)
import { app, BrowserWindow } from "electron";
import path from "node:path";
import { fileURLToPath } from "node:url";

const __dirname = path.dirname(fileURLToPath(import.meta.url));

function createWindow() {
  const win = new BrowserWindow({
    width: 960,
    height: 720,
    title: "DeskNotes",
    webPreferences: {
      preload: path.join(__dirname, "preload.js"),
      contextIsolation: true, // default; keep it
      nodeIntegration: false, // default; keep it
      sandbox: true,
    },
  });

  if (process.env.ELECTRON_START_URL) {
    win.loadURL(process.env.ELECTRON_START_URL); // Vite dev server
  } else {
    win.loadFile(path.join(__dirname, "../dist/index.html"));
  }
}

app.whenReady().then(() => {
  createWindow();
  app.on("activate", () => {
    if (BrowserWindow.getAllWindows().length === 0) createWindow();
  });
});

app.on("window-all-closed", () => {
  if (process.platform !== "darwin") app.quit();
});
```

`loadURL` in development points at Vite (`http://localhost:5173`) so React Fast Refresh works inside the desktop window. Production loads the built `index.html` from disk (`file://`).

macOS convention: closing the last window does **not** quit the app; Cmd+Q or `app.quit()` does. Windows/Linux usually quit when the last window closes. The snippet above matches that.

### webPreferences you should not “just enable”

| Flag | Safe default | If you flip it |
| --- | --- | --- |
| `contextIsolation` | `true` | Preload and page share one JS world — XSS can reach Node-shaped APIs |
| `nodeIntegration` | `false` | Renderer can `require("fs")` — treat any XSS as full disk access |
| `sandbox` | `true` | Looser Chromium sandbox |
| `webSecurity` | `true` | Turns off same-origin checks; almost never needed |

Old tutorials set `nodeIntegration: true` and skip preload. That is the 2016 pattern. Do not copy it into a React app in 2026.

## Preload — the airlock between React and Node

**Preload** is a script that runs **before** the page’s JavaScript, in a privileged but limited world. It can use `require` / Node APIs **and** a subset of DOM (`window`). It is the only place that should talk to both sides.

`contextBridge.exposeInMainWorld` copies a **safe, function-only** object onto `window` in the page.

```js
// electron/preload.js
const { contextBridge, ipcRenderer } = require("electron");

contextBridge.exposeInMainWorld("notes", {
  read: () => ipcRenderer.invoke("notes:read"),
  save: (text) => ipcRenderer.invoke("notes:save", text),
  pickFile: () => ipcRenderer.invoke("notes:pick"),
});
```

React then sees:

```ts
// src/electron.d.ts
export type NotesApi = {
  read: () => Promise<string>;
  save: (text: string) => Promise<void>;
  pickFile: () => Promise<string | null>;
};

declare global {
  interface Window {
    notes: NotesApi;
  }
}
```

Rules that keep this an airlock:

- Expose **functions**, not `ipcRenderer` itself. If you expose `ipcRenderer`, any script in the page can invoke **any** channel.
- Validate arguments in **main**, not only in React. The renderer is hostile (XSS, extensions, future bugs).
- Prefer `invoke` / `handle` (request/response) over raw `send` / `on` unless you need push events (progress, menu clicks).

## IPC — how the two processes talk

**IPC** = inter-process communication. Electron uses Chromium’s IPC under the hood. Your API is `ipcMain` + `ipcRenderer`.

Data is **structured-cloned** (same idea as `postMessage`). You can send JSON-like objects, `ArrayBuffer`, etc. You cannot send functions, class instances with methods, or DOM nodes.

### Request / response (`invoke` + `handle`)

This is the pattern for “React wants a result.”

```js
// electron/main.js
import { app, ipcMain, dialog } from "electron";
import fs from "node:fs/promises";
import path from "node:path";

const notesPath = () => path.join(app.getPath("userData"), "notes.txt");

ipcMain.handle("notes:read", async () => {
  try {
    return await fs.readFile(notesPath(), "utf8");
  } catch (err) {
    if (err.code === "ENOENT") return "";
    throw err;
  }
});

ipcMain.handle("notes:save", async (_event, text) => {
  if (typeof text !== "string") throw new Error("notes:save expects a string");
  if (text.length > 1_000_000) throw new Error("note too large");
  await fs.mkdir(path.dirname(notesPath()), { recursive: true });
  await fs.writeFile(notesPath(), text, "utf8");
});

ipcMain.handle("notes:pick", async (event) => {
  const win = event.sender.getOwnerBrowserWindow();
  const result = await dialog.showOpenDialog(win ?? undefined, {
    properties: ["openFile"],
    filters: [{ name: "Text", extensions: ["txt", "md"] }],
  });
  if (result.canceled || !result.filePaths[0]) return null;
  return fs.readFile(result.filePaths[0], "utf8");
});
```

`app.getPath("userData")` is the right place for app files (`~/Library/Application Support/DeskNotes` on macOS). Do not write next to the `.app` bundle — the OS may make that directory read-only.

`event.sender` is the renderer that called. Attach dialogs to **that** window so the sheet appears on the right display.

### Fire and forget (`send` + `on`)

Main pushes into a window (menu “Save”, tray “Show”):

```js
win.webContents.send("notes:from-menu", { action: "save" });
```

Preload should still wrap this — do not let the page subscribe to arbitrary channels:

```js
contextBridge.exposeInMainWorld("notes", {
  onFromMenu: (callback) => {
    const listener = (_event, payload) => callback(payload);
    ipcRenderer.on("notes:from-menu", listener);
    return () => ipcRenderer.removeListener("notes:from-menu", listener);
  },
});
```

React:

```jsx
useEffect(() => {
  return window.notes.onFromMenu((payload) => {
    if (payload.action === "save") void persist();
  });
}, []);
```

## A React UI on the renderer

Renderer entry is a normal Vite + React app. The only Electron-specific piece is calling `window.notes`.

```tsx
// src/App.tsx
import { useEffect, useState } from "react";

export function App() {
  const [text, setText] = useState("");
  const [status, setStatus] = useState("idle");

  useEffect(() => {
    let cancelled = false;
    window.notes.read().then((value) => {
      if (!cancelled) setText(value);
    });
    return () => {
      cancelled = true;
    };
  }, []);

  async function persist() {
    setStatus("saving");
    await window.notes.save(text);
    setStatus("saved");
  }

  async function openFromDisk() {
    const file = await window.notes.pickFile();
    if (file != null) setText(file);
  }

  return (
    <main>
      <h1>DeskNotes</h1>
      <textarea value={text} onChange={(e) => setText(e.target.value)} rows={20} />
      <p>
        <button type="button" onClick={() => void persist()}>
          Save
        </button>
        <button type="button" onClick={() => void openFromDisk()}>
          Open…
        </button>
        <span>{status}</span>
      </p>
    </main>
  );
}
```

```tsx
// src/main.tsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { App } from "./App";

createRoot(document.getElementById("root")!).render(
  <StrictMode>
    <App />
  </StrictMode>,
);
```

Guard the API if you also run the same React tree in a browser tab:

```ts
const notes =
  window.notes ?? {
    read: async () => "",
    save: async () => {},
    pickFile: async () => null,
  };
```

That split is useful: **Vite in Chrome** for CSS, **Electron window** for `fs`.

## Dev loop: Vite + Electron together

Two processes in development:

1. Vite serves React (`http://localhost:5173`)
2. Electron main loads that URL

A minimal `package.json` shape:

```json
{
  "name": "desk-notes",
  "main": "electron/main.js",
  "type": "module",
  "scripts": {
    "dev": "concurrently \"vite\" \"wait-on http://localhost:5173 && electron .\"",
    "build": "vite build && electron-builder"
  }
}
```

Set `ELECTRON_START_URL=http://localhost:5173` for the `loadURL` branch. Tools like **electron-vite** and **Electron Forge** automate ESM vs CJS, TypeScript for main/preload, and HMR for the **main** process (restart the app when `main.js` changes — React HMR does not reload Node).

### Why main and renderer are bundled separately

| Bundle | Runs in | Can import |
| --- | --- | --- |
| `main.js` | Node | `electron`, `node:fs`, native addons |
| `preload.js` | Isolated world + Node (limited) | `electron` (`contextBridge`, `ipcRenderer`) |
| `renderer` (Vite) | Chromium | React, CSS — **not** `electron` |

If Vite tries to bundle `import { app } from "electron"` into the React graph, the browser build breaks. Keep `electron` imports **only** in main and preload. Mark `electron` as external in the main/preload build.

## Native surface area you actually use

Once IPC is in place, main can call the rest of the desktop API.

### Menus

```js
import { Menu, shell } from "electron";

const template = [
  {
    label: "File",
    submenu: [
      {
        label: "Save",
        accelerator: "CmdOrCtrl+S",
        click: (_item, browserWindow) => {
          browserWindow?.webContents.send("notes:from-menu", { action: "save" });
        },
      },
      { type: "separator" },
      { role: "quit" },
    ],
  },
  { role: "editMenu" },
  {
    label: "Help",
    submenu: [
      {
        label: "Website",
        click: () => shell.openExternal("https://priyadarshi.dev"),
      },
    ],
  },
];

Menu.setApplicationMenu(Menu.buildFromTemplate(template));
```

`role: "editMenu"` gives you undo/copy/paste that match the OS. Always `openExternal` for http(s) links instead of loading random sites inside your `BrowserWindow` (session cookies, XSS surface).

### User paths

```js
app.getPath("home");
app.getPath("documents");
app.getPath("userData");
app.getPath("temp");
```

### Single instance

```js
const locked = app.requestSingleInstanceLock();
if (!locked) {
  app.quit();
} else {
  app.on("second-instance", () => {
    const win = BrowserWindow.getAllWindows()[0];
    win?.show();
    win?.focus();
  });
}
```

Without this, every dock click can spawn another copy of your React app.

## Packaging — turning it into a laptop app

**electron-builder** or **Electron Forge** wrap:

- Chromium + Node + your `dist/`
- Platform icons (`.icns`, `.ico`)
- Code signing (macOS notarization, Windows Authenticode)
- Auto-update (`electron-updater` + a GitHub Releases feed, or a private CDN)

Output is not “a website with a shortcut.” It is an OS application. Users install it once; you ship updates as new versions.

`package.json` needs `"main"` pointing at the **compiled** main process file. If `main` is missing, Electron looks for `index.js` at the root and fails in confusing ways.

## Electron vs PWA vs “real native”

| | Electron | PWA | Swift / WinUI |
| --- | --- | --- | --- |
| UI stack | Chromium + React | Browser + React | Platform UI |
| File system | Full, via main | Sandboxed / picker | Full |
| Installer size | Large | Tiny (it’s a site) | Small–medium |
| App stores | Possible, extra work | Install from browser | First-class |
| Offline | You control it | Service worker | You control it |
| One codebase, 3 OSes | Yes | Yes (browser) | No |

Use Electron when you need **Node + a real window** and you already have (or want) a **React** UI. Use a PWA when the browser is enough. Use native when you need tiny RAM, deep OS widgets, or store review that punishes embedded Chromium.

## Security checklist (interview-ready)

1. `contextIsolation: true`, `nodeIntegration: false`
2. Preload exposes a **whitelist of functions**, never `ipcRenderer`
3. Main **validates** every IPC argument (type, length, path)
4. Do not build file paths from renderer strings without resolving them **inside** `userData` (path traversal: `../../`)
5. `shell.openExternal` only for `https:` (and maybe `mailto:`)
6. Disable or tightly control `remote` / `enableRemoteModule` (removed / obsolete)
7. Treat `webContents` like a browser: CSP, no `unsafe-eval` if you can avoid it
8. Keep Electron **current** — you ship Chromium; old Electron is old Chrome

Path allowlist example:

```js
import path from "node:path";

function insideUserData(filePath) {
  const root = app.getPath("userData");
  const resolved = path.resolve(root, filePath);
  if (!resolved.startsWith(root + path.sep) && resolved !== root) {
    throw new Error("path escapes userData");
  }
  return resolved;
}
```

## Mental model to keep

**React paints pixels. Main is the operating system. Preload is the contract. IPC is the wire.**

If a feature needs the disk, a menu, or a tray icon, it does not go in a React component. It goes in main, with a one-line function on `window` that the component can call.

## Interview answers

<details>
<summary>What is Electron?</summary>

A framework that bundles Chromium and Node.js so you can build desktop apps with web technologies. The UI runs in a renderer (browser). Privileged OS work runs in a single main process (Node). They talk over IPC.

</details>

<details>
<summary>Main process vs renderer process?</summary>

Main: one Node process, no DOM, creates windows, owns `fs` / dialogs / menus. Renderer: Chromium per window, has a DOM, runs React. Renderers are untrusted; they should not get Node integration.

</details>

<details>
<summary>What is a preload script?</summary>

A script that runs before page JS, with access to `contextBridge` and `ipcRenderer`. It exposes a small API on `window` so React never imports `electron` and never sees Node.

</details>

<details>
<summary>Why not `nodeIntegration: true`?</summary>

Any XSS in the page (malicious markdown, a compromised npm UI lib) could `require("child_process")`. Isolation + a narrow preload API contains that to the functions you wrote.

</details>

<details>
<summary>How does React fit?</summary>

React is only the renderer UI. Data that lives on disk is loaded and saved through `window.*` APIs that `invoke` main. Same component model as the web; different I/O boundary.

</details>

<details>
<summary>invoke vs send?</summary>

`invoke` / `handle` is async request/response (like `fetch`). `send` / `on` is one-way events (menu clicked, download progress). Prefer `invoke` for CRUD.

</details>
