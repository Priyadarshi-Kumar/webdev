**JSON-RPC 2.0** is a tiny convention: call `method` with `params`, match the reply by `id`. A **notification** is the same shape with **no** `id` — fire and forget.

MCP messages are JSON-RPC. REST is a different style (URLs and HTTP verbs). You can tunnel JSON-RPC *over* HTTP; the body is still this object.

## Request and result

**Plain English:** Request and result — definition, example, and where you will see it.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": { "name": "get_time", "arguments": {} }
}
```

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [{ "type": "text", "text": "2026-08-14T04:30:00Z" }]
  }
}
```

The `id` pairs them. If two calls are in flight, the host does not guess which reply is which.

## Errors and notifications

**Plain English:** Errors and notifications — definition, example, and where you will see it.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": { "code": -32601, "message": "Method not found" }
}
```

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed"
}
```

No `id` on the second object → do not send a result. The <Term id="mcp-client">client</Term> just re-runs `tools/list`.

MCP adds capability negotiation and (on HTTP) extra headers. The body is still JSON-RPC. You can log it like any other JSON API.
