## What this is

`this` is a hidden extra argument the engine fills in when your function runs — not a variable you declare, and not “the object the function lives on.”

If you treat `this` like Python’s `self` that the caller passes in, the language suddenly makes sense. The function body just reads whatever value the engine put in that slot.

## The call site picks this

### A call is more than a list of arguments

When JavaScript runs `fn(a, b)`, the engine actually does something closer to:

```js
fn.call(thisArg, a, b);
```

You do not write `thisArg`. The engine picks it from **how** you wrote the call:

| How you call | What `this` becomes (sloppy / non-strict) |
| --- | --- |
| `fn()` | `globalThis` (`window` in a browser) |
| `obj.fn()` | `obj` |
| `fn.call(x)` / `fn.apply(x)` | `x` (boxed if it is a primitive) |
| `new Fn()` | a fresh object whose prototype is `Fn.prototype` |
| `() => { this }` | whatever `this` was **outside** the arrow — arrows do not get their own slot |

In **strict mode** (`"use strict"` or ES modules, which are strict), a bare `fn()` sets `this` to `undefined` instead of the global object. That is why `this.foo` in a module-level function throws instead of silently writing to `window`.

### The function does not own this

```js
const user = {
  name: "Ada",
  greet() {
    return `hi ${this.name}`;
  },
};

const greet = user.greet;

user.greet(); // "hi Ada"  — call site is user.greet
greet();      // "hi undefined" (or throw in strict) — call site is greet()
```

Same function object. Different call site. Different `this`. Losing the `obj.` on the left is the classic bug: you passed the function, not the method.

## The four bindings

Think of a tiny dispatcher the engine could run before entering the function. This is teaching code, not a real VM — but the rules match.

```js
function resolveThis({ kind, fn, object, explicit, isStrict }) {
  if (fn.isArrow) {
    return fn.capturedThis; // lexical — baked in when the arrow was created
  }

  if (kind === "new") {
    const instance = Object.create(fn.prototype ?? null);
    return instance;
  }

  if (kind === "explicit") {
    if (explicit == null) return isStrict ? explicit : globalThis;
    return typeof explicit === "object" ? explicit : Object(explicit);
  }

  if (kind === "method") {
    return object;
  }

  // kind === "bare"
  return isStrict ? undefined : globalThis;
}
```

### Implicit: the object before the dot

```js
const counter = {
  n: 0,
  inc() {
    this.n += 1;
    return this.n;
  },
};

counter.inc(); // this === counter
```

The lookup `counter.inc` finds the function. The **call** `counter.inc()` is what sets `this` to `counter`. Nested objects use the **receiver** — the object you actually called the method on — not necessarily the object that stored the function:

```js
const proto = {
  kind: "proto",
  label() {
    return this.kind;
  },
};

const child = Object.create(proto);
child.kind = "child";
child.label(); // "child" — this is the receiver
```

### Explicit: you pass thisArg

```js
function greet(punct) {
  return `hi ${this.name}${punct}`;
}

const ada = { name: "Ada" };
greet.call(ada, "!");   // "hi Ada!"
greet.apply(ada, ["?"]); // "hi Ada?"
const bound = greet.bind(ada, ".");
bound(); // "hi Ada."
```

`bind` does not run the function. It returns a **new** function whose `this` (and any prefix arguments) are already filled in.

### new: this is a fresh instance

```js
function Box(value) {
  this.value = value;
}

const a = new Box(1);
a.value; // 1
a instanceof Box; // true
```

`new` does four jobs: create an object, wire its prototype to `Fn.prototype`, call `Fn` with `this` set to that object, then return the object (unless the constructor returned a different object).

### Arrows: no this slot

```js
const panel = {
  id: "nav",
  items: [1, 2],
  broken() {
    return this.items.map(function (n) {
      return `${this.id}-${n}`; // this is undefined / global — not panel
    });
  },
  ok() {
    return this.items.map((n) => `${this.id}-${n}`); // arrow reads panel's this
  },
};
```

An arrow function does not get its own `this`. It reuses whatever `this` meant in the surrounding code. That is why `map` callbacks as arrows see the method’s `this`, and why you cannot `new` an arrow.

## Implement call, apply, and bind

The trick: temporarily hang the function on the target object, call it as a method (so implicit binding kicks in), then clean up.

### myCall

```js
Function.prototype.myCall = function myCall(thisArg, ...args) {
  if (typeof this !== "function") {
    throw new TypeError("myCall must be called on a function");
  }

  const target =
    thisArg == null ? globalThis : Object(thisArg);
  const key = Symbol("myCall");
  target[key] = this;

  try {
    return target[key](...args);
  } finally {
    delete target[key];
  }
};

function intro(role) {
  return `${this.name} · ${role}`;
}

intro.myCall({ name: "Ada" }, "engineer");
// "Ada · engineer"
```

`Symbol` as the property name avoids clobbering `target.call` or anything the object already has. `Object(thisArg)` wraps primitives so `"hi".myCall` still has a place to put the function — close to what `call` does in sloppy mode.

### myApply

```js
Function.prototype.myApply = function myApply(thisArg, argList) {
  const args = argList == null ? [] : Array.from(argList);
  return this.myCall(thisArg, ...args);
};

intro.myApply({ name: "Ada" }, ["engineer"]);
```

`apply` is `call` with the rest of the arguments in one array-like.

### myBind

```js
Function.prototype.myBind = function myBind(thisArg, ...preset) {
  if (typeof this !== "function") {
    throw new TypeError("myBind must be called on a function");
  }

  const fn = this;

  function bound(...later) {
    const args = preset.concat(later);
    if (new.target) {
      return new fn(...args);
    }
    return fn.myCall(thisArg, ...args);
  }

  bound.prototype = Object.create(fn.prototype);
  return bound;
};

const adaIntro = intro.myBind({ name: "Ada" });
adaIntro("engineer"); // "Ada · engineer"
```

Real `bind` also handles `new bound()`: constructing a bound function ignores the bound `this` and uses the new instance instead. The `new.target` branch above copies that rule.

## Implement new

```js
function myNew(Fn, ...args) {
  if (typeof Fn !== "function") {
    throw new TypeError("myNew needs a constructor");
  }

  const instance = Object.create(Fn.prototype);
  const result = Fn.myCall(instance, ...args);
  return result !== null && (typeof result === "object" || typeof result === "function")
    ? result
    : instance;
}

function User(name) {
  this.name = name;
}

const u = myNew(User, "Ada");
u.name; // "Ada"
Object.getPrototypeOf(u) === User.prototype; // true
```

If the constructor `return`s an object, that object wins. If it returns a primitive (or nothing), the engine keeps the instance it created. That is why `return this` in a constructor is redundant, and why `return { ok: true }` replaces the instance.

## this in classes

A `class` is a function with its methods parked on `Fn.prototype`, so the same four rules apply — with two wrinkles.

### Methods are shared, fields are per-instance

```js
class Counter {
  count = 0;                       // own property on each instance
  inc() { this.count += 1; }       // one function on Counter.prototype
  incArrow = () => { this.count += 1; }; // a new function per instance
}
```

`inc` is an ordinary method: calling `c.inc()` sets `this` to `c`, and detaching it loses that. `incArrow` is a class field holding an arrow, so it captured `this` when the instance was built and survives detachment — at the cost of one function object per instance. That is the whole tradeoff behind auto-binding handlers.

```js
const c = new Counter();
const loose = c.inc;
loose();        // TypeError — class bodies are strict, so this is undefined
const bound = c.incArrow;
bound();        // fine — the arrow captured the instance
```

### Class bodies are always strict

There is no sloppy-mode fallback inside a class. A detached method gets `undefined`, not `globalThis`, so the failure is a loud `TypeError` rather than a silent write to the global object. [Prototypes](/blog/prototype-and-proto) covers where each member actually lands.

## Where this goes missing

Every one of these is the same bug — the function was extracted from its call site.

### Callbacks and timers

```js
setTimeout(user.greet, 0);          // detached — this is not user
setTimeout(() => user.greet(), 0);  // call site preserved
setTimeout(user.greet.bind(user), 0);
```

### DOM event handlers

In a regular function used as a listener, `this` is the element the listener is attached to — the same value as `event.currentTarget`. Convert it to an arrow and you lose that, so read `event.currentTarget` explicitly if you want both.

```js
button.addEventListener("click", function () {
  this;                 // the button
});

button.addEventListener("click", (event) => {
  this;                 // enclosing this — NOT the button
  event.currentTarget;  // the button
});
```

### Array methods accept a thisArg

`map`, `filter`, `forEach`, `some`, `every`, and `find` all take an optional second argument used as `this` inside the callback. It only works for regular functions, since arrows ignore it.

```js
[1, 2].map(function (n) { return this.factor * n; }, { factor: 10 }); // [10, 20]
```

### React

Function components never read `this`, which is one reason hooks removed a whole category of bug. In class components you still need `this.handleClick = this.handleClick.bind(this)` in the constructor, or a class field arrow.

## What the spec adds (optional)

The spec uses a few labels for the same story:

- **`this` environment slot** — where the value lives for the duration of the call
- **`[[ThisMode]]`** — `lexical` (arrows), `strict`, or `global`
- **`[[ThisValue]]`** — the actual value (primitives get wrapped in sloppy mode)
- **Reference** — `obj.fn` is not just the function; it carries `{ base: obj, name: "fn" }`. Calling a Reference uses `base` as `this`. A bare identifier has no base, so you get `undefined` / global.

One sentence to remember: **`this` is chosen from the call expression, stored on the running context, then read by the body.**

```js
// these two are the same idea
obj.fn(1);
fn.call(obj, 1);
```

Methods, callbacks, and `setTimeout(obj.fn, 0)` all drop the Reference: you extracted the function, so there is no `base`. Bind it, wrap it in an arrow, or call it as `obj.fn()` if you need that object.

## A compact cheat sheet

```js
obj.method();           // this → obj
const f = obj.method;
f();                    // this → undefined (strict) / global (sloppy)
f.call(obj);            // this → obj
const g = f.bind(obj);
g();                    // this → obj
new F();                // this → new instance
() => this;             // this → enclosing this (not a new one)
```

Write `myCall` / `myBind` / `myNew` once. After that, `this` is just the argument you forgot you were passing.

## Interview answers

<details>
<summary>What determines the value of <code>this</code>?</summary>

The call site, not the definition site. Four rules, in precedence order: `new` creates a fresh instance and binds it; `call`, `apply`, or `bind` set it explicitly; a method call binds the object before the dot; and a bare call gives `undefined` in strict mode or `globalThis` in sloppy mode. Arrow functions sit outside all four — they have no `this` slot and read the enclosing scope's.

</details>

<details>
<summary>Why does a detached method lose <code>this</code>?</summary>

`obj.fn` evaluates to just the function; the binding comes from the call expression `obj.fn()`, not from the function itself. Assigning it to a variable or passing it to `setTimeout` drops the receiver, so the later call is a bare call. Fix it with `bind`, an arrow wrapper, or by calling it as `obj.fn()`.

</details>

<details>
<summary>How do <code>call</code>, <code>apply</code>, and <code>bind</code> differ?</summary>

`call` and `apply` both invoke immediately and differ only in argument shape — `call` takes them individually, `apply` takes an array. `bind` invokes nothing: it returns a new function with `this` and any leading arguments pre-filled, which you call later.

</details>

<details>
<summary>Can you use <code>new</code> on an arrow function?</summary>

No. Arrows have no `this` slot of their own and no `prototype` property, both of which `new` requires. It throws a `TypeError`.

</details>

<details>
<summary>What does <code>new</code> actually do?</summary>

Four steps: create an empty object, set its prototype to the constructor's `prototype` property, call the constructor with `this` bound to that object, and return the object — unless the constructor explicitly returned a different object, in which case that one wins. A returned primitive is ignored.

</details>

<details>
<summary>Why is a class field arrow different from a prototype method?</summary>

A method lives once on the prototype and is shared, so it depends on the call site for `this`. A class field arrow is created per instance during construction and captures that instance permanently, so it survives being detached — at the cost of one function object per instance.

</details>
