**CI** is an automated job (GitHub Actions, Netlify, GitLab CI) that clones your repo on a **fresh** VM, installs dependencies, and runs tests or a build. It has no leftover `node_modules` from yesterday.

That is why the <Term id="lockfile">lockfile</Term> matters: the robot should install **exactly** what you committed.

## A minimal GitHub Actions job

**Plain English:** A minimal GitHub Actions job — definition, example, and where you will see it.

```yaml
# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: corepack enable
      - run: pnpm install --frozen-lockfile
      - run: pnpm test
      - run: pnpm build
```

Never run a command in CI that **rewrites** the lockfile (`npm install` can). Use `npm ci` / frozen / immutable installs.

## Why “works on my machine” fails here

**Plain English:** Why “works on my machine” fails here — definition, example, and where you will see it.

Your laptop has global CLIs, a warm pnpm store, and Node 22. The VM has none of that unless you install it. <Term id="corepack">Corepack</Term> + `packageManager` makes Yarn/pnpm versions match. `engines` in `package.json` can fail the job on the wrong Node:

```json
{
  "engines": {
    "node": ">=22"
  }
}
```

## CI vs CD

**Plain English:** CI vs CD — definition, example, and where you will see it.

**CI** = merge is safe (lint, test, typecheck). **CD** (continuous delivery) = that green build is deployed (Netlify on `main`, for this site). Same lockfile rules apply to the deploy image.
