A **microfrontend** is a piece of the UI that a team can ship **without rebuilding the whole product**. Checkout, the cart drawer, the admin grid — each can be a separate Vite (or Webpack) app with its own `package.json`, CI, and URL.

## Host and remotes

**Plain English:** Host and remotes — definition, example, and where you will see it.

Composition is the rest of the story. The **host** owns the shell (nav, auth, routing). A **remote** exposes a component or a route. The host loads that JS at **runtime** (<Term id="module-federation">Module Federation</Term>, an iframe, a web component) or at **build time** (a workspace package). Runtime is the usual meaning of “microfrontend.”

```tsx
// host route — cart is another deployed app
const MiniCart = lazy(() => import("cart/MiniCart"));

export function Header() {
  return (
    <Suspense fallback={null}>
      <MiniCart />
    </Suspense>
  );
}
```

Deploy `cart` at 3pm without rebuilding `shell`. That is the payoff. The cost is shared libraries, version skew, and a harder local story.

## One React

**Plain English:** One React — definition, example, and where you will see it.

Two Reacts on one page break hooks. Shared libraries must be **one copy**, usually listed as a <Term id="peer-dependency">peer</Term> and as `shared` in federation config.

```ts
shared: {
  react: { singleton: true, requiredVersion: "^19.0.0" },
  "react-dom": { singleton: true, requiredVersion: "^19.0.0" },
}
```

## Not a monorepo

**Plain English:** Not a monorepo — definition, example, and where you will see it.

A <Term id="monorepo">monorepo</Term> is not a microfrontend. One repo with `apps/web` and `libs/widgets` is still **one deploy** unless you also split hosts and remotes. You can keep remotes in one git repo (this is common) and still publish two URLs.

This site is a monorepo on purpose. It does not ship microfrontends.
