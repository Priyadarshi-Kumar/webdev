A **bundler** takes the files you write (`index.html`, `App.tsx`, CSS, images) and produces something a browser can load: fewer requests, modern syntax rewritten for older browsers, and imports that actually resolve. **Webpack** and **Vite** both do that job. They do not do it the same way.

Webpack’s classic loop is: **walk every import, build one (or a few) giant bundles, then serve**. Vite’s loop is: **in development, skip the giant bundle** — serve your source as native ES modules and only pre-bundle `node_modules`. For `vite build`, it still bundles (with **Rollup**) so production is cacheable and small.

This site’s app is Vite (`apps/web/vite.config.ts`). Below is enough to run a tiny Vite app, read a Webpack config next to it, and explain the difference in an interview.

## Mental model

### What the browser already understands

Modern browsers can load:

```html
<script type="module" src="/src/main.ts"></script>
```

A module graph is then just `import` / `export`. You do **not** need a bundler for that to *run* on localhost — you need one because TypeScript, JSX, CSS modules, path aliases, and npm packages are not what the browser asked for.

Vite leans on that native graph in **dev**. Webpack historically assumed the browser could not, so it compiled the whole graph into `bundle.js` first.

### Two commands, two pipelines

| Command | Vite | Webpack (typical CRA / webpack-dev-server) |
| --- | --- | --- |
| Dev | esbuild pre-bundles deps; your source is transformed **on demand** as you request the file | Compiles (most of) the graph into bundles, then serves them. First compile is the wait. |
| Prod | Rollup (or Rolldown in newer Vite) emits hashed chunks | webpack emits hashed chunks |

**esbuild** is a Go compiler used as a *transform* (TS/JSX → JS) and to pre-bundle libraries. It is not the production bundler in Vite 5/6. Do not say “Vite uses esbuild in production” unless you mean a plugin that opted in.

## A small Vite app

Three files. From an empty folder:

```bash
pnpm add -D vite
```

`index.html` is the **real entry**. Vite treats it as the app shell, not a leftover after bundling.

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <title>Vite demo</title>
  </head>
  <body>
    <div id="app"></div>
    <script type="module" src="/src/main.ts"></script>
  </body>
</html>
```

```ts
// src/main.ts
import { greet } from "./greet";

document.querySelector("#app")!.textContent = greet("Vite");
```

```ts
// src/greet.ts
export function greet(name: string) {
  return `hello ${name}`;
}
```

```ts
// vite.config.ts
import { defineConfig } from "vite";

export default defineConfig({
  server: { port: 5173 },
  build: { outDir: "dist" },
});
```

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  }
}
```

`pnpm dev` starts in milliseconds. Open the Network tab: you will see **many small `.ts` requests**, not one `main.js`. Vite’s middleware compiles `main.ts` when the browser asks for it, injects HMR, and rewrites `from "./greet"` to a URL.

`pnpm build` writes hashed files under `dist/`. `pnpm preview` serves that folder so you can check the production graph locally.

### React in a few lines

```ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
});
```

The plugin runs Babel or oxc (depending on Vite version) for Fast Refresh. JSX files stay modules in dev; they are bundled for prod.

## How Webpack does the same job

Webpack’s entry is usually a **JS file**, not HTML. HTML is generated by a plugin.

```js
// webpack.config.js
const path = require("node:path");
const HtmlWebpackPlugin = require("html-webpack-plugin");

module.exports = {
  entry: "./src/main.ts",
  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "[name].[contenthash].js",
    clean: true,
  },
  resolve: { extensions: [".ts", ".js"] },
  module: {
    rules: [
      {
        test: /\.ts$/,
        use: "ts-loader",
        exclude: /node_modules/,
      },
    ],
  },
  plugins: [new HtmlWebpackPlugin({ template: "./index.html" })],
  devServer: { port: 8080, hot: true },
};
```

On `webpack serve`, loaders run across the graph **before** the page is useful. A mid-size React app can sit on “compiling…” for tens of seconds. HMR then patches the bundle. That model is battle-tested (code splitting, Module Federation, years of plugins). It is also why Vite felt like a cheat when it landed.

## Where they actually differ

### Startup and HMR

**Webpack:** change one module → rebuild the affected parts of the **bundle** → push an update. Cost grows with graph size.

**Vite:** change `greet.ts` → re-transform **that file** → the browser re-imports that module (or accepts an HMR patch). Unrelated routes you never opened were never compiled.

Cold start stays flat as the app grows. First visit of a heavy route still pays a transform; you just do not pay for the whole app up front.

### Dependencies vs your source

`lodash`, `react`, and other CJS packages are a poor fit for native ESM (hundreds of tiny files, `require`, missing extensions). Vite **pre-bundles** them with esbuild into a few ESM files in `node_modules/.vite`. Your source stays unbundled in dev.

Webpack puts **your code and vendor code** through the same loader pipeline unless you split chunks. `splitChunks` is a production optimization, not a replacement for Vite’s “deps vs source” split.

### Config surface

Webpack is a **graph of loaders and plugins**. CSS, images, TypeScript, SVGs — each is a `module.rules` entry. Power and ceremony.

Vite is **conventions plus plugins**: TS and JSX work, `import url from "./x.svg"` works, CSS `import` works, `import.meta.env.VITE_*` is the env story. You add a plugin when the convention is not enough (`@vitejs/plugin-react`, `vite-plugin-svgr`, MDX).

### Production output

Both emit hashed JS/CSS and can split async `import()`. Vite’s production bundler is Rollup: tree-shaking is ESM-first and usually excellent. Webpack’s tree-shaking depends on `sideEffects` in <Term id="package-json">`package.json`</Term> and how modules are written (CJS is harder to shake).

Webpack still wins some **library / federation** setups. Vite can emit a library (`build.lib`) but Webpack’s Module Federation ecosystem is older and wider.

### CommonJS vs ESM

Vite wants **ESM** (`"type": "module"`, `import`). Some old plugins only speak CJS. Webpack swallowed CJS for a decade; that is why ancient loaders still work.

If a package breaks Vite with `require is not defined` or a dual-package hazard, the usual fix is `optimizeDeps.include` / `ssr.noExternal`, or swapping the package — not “Vite cannot bundle.”

## Env vars and `import.meta`

Vite only exposes variables prefixed with `VITE_` (unless you change `envPrefix`):

```ts
// .env
VITE_API = https://api.example.com

// src/api.ts
const base = import.meta.env.VITE_API;
```

Webpack / CRA used `process.env.REACT_APP_*` and DefinePlugin. Do not copy `process.env.NODE_ENV` checks into Vite source and expect Node’s `process` in the browser — Vite defines `import.meta.env.MODE`, `DEV`, `PROD`, `SSR`.

## When Webpack is still the right tool

- An existing CRA or custom Webpack app that already works; migrate when the **dev-server wait** hurts, not on principle.
- **Module Federation** as the org standard for microfrontends (this site does not use that — and should not).
- Loaders that have no Vite plugin and would take weeks to replace.

For a new SPA, a Vite + React (or Vue) app, or a <Term id="monorepo">monorepo</Term> where <Term id="nx">Nx</Term> already shells out to `vite`, Vite is the default in 2026. Vitest even reuses the same config and transform pipeline for tests.

## Interview answers

<details>
<summary>What is Vite, and why is it faster than Webpack in development?</summary>

Vite is a dev server plus a production bundler. In development it serves source as native ES modules and transforms files on demand (esbuild for TS/JSX). Webpack bundles the application graph before the page loads, so the first compile scales with app size. Vite also pre-bundles `node_modules` once so the browser is not fetching thousands of CommonJS files.

</details>

<details>
<summary>Does Vite bundle at all?</summary>

Yes, for production (`vite build`), using Rollup. Development is unbundled (plus a dependency pre-bundle). Saying “Vite never bundles” is wrong.

</details>

<details>
<summary>What is the difference between esbuild and Rollup in Vite?</summary>

esbuild is used to pre-bundle dependencies and to transpile TS/JSX quickly in dev. Rollup produces the optimized production output (code splitting, tree-shaking, hashed assets). They are different tools in one pipeline, not two names for the same step.

</details>

<details>
<summary>Why is <code>index.html</code> the Vite entry?</summary>

The browser starts at HTML. Vite uses that file as the module graph root (`script type="module"`). Webpack usually starts at a JS entry and injects a script tag via HtmlWebpackPlugin. Same end result; different root of the graph.

</details>

<details>
<summary>How does HMR differ?</summary>

Webpack HMR patches modules inside the compiled bundle. Vite HMR invalidates ESM modules the browser already loaded. Because Vite did not compile unused routes, a save in a leaf file does not wait on the rest of the app.

</details>

<details>
<summary>When would you still choose Webpack?</summary>

Large inherited configs, Module Federation, or a plugin/loader with no Vite equivalent. For a greenfield SPA, Vite (or a framework on top of it) is the usual choice.

</details>
